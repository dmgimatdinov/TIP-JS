**Центральная идея лекции:** сетевая операция не выполняется мгновенно. Асинхронный код не делает программу параллельной — он позволяет не блокировать выполнение, пока результат ещё не готов. HTTP-ответ требует явной проверки статуса, заголовков и формата тела: успешный статус `fetch` не означает, что данные пригодны для использования.

## 1. Место лекции в курсе

В ПР1–ПР4 приложение работало с данными в памяти процесса и в `localStorage`. Все операции были синхронными: вызов функции возвращал результат сразу. В ПР5 источник данных меняется — задачи запрашиваются у HTTP-сервера, и ответ приходит через неопределённое время. В ПР6 к чтению добавляются операции изменения (POST, PATCH, DELETE), состояния интерфейса и защита от устаревших ответов.

Лекция закрывает разрыв между синхронным кодом, который студенты уже пишут, и асинхронной природой сетевых операций.

### 1.1. Результаты обучения

После изучения материала необходимо уметь:

- объяснять порядок выполнения синхронного кода, микрозадач Promise и задач таймеров;
- использовать `Promise`, `async`/`await` без потери ошибок;
- различать успешный HTTP-ответ, HTTP-ошибку, сетевую ошибку и неверный формат ответа;
- формировать URL и query-параметры стандартными средствами (`URL`, `URLSearchParams`);
- проверять `Response.ok`, статус и `Content-Type` до разбора JSON;
- ограничивать время ожидания (`AbortSignal.timeout`) и отменять запрос (`AbortController`);
- загружать независимые ресурсы параллельно через `Promise.all`;
- разделять общий HTTP-клиент и предметный API;
- выводить состояния интерфейса `loading`, `ready`, `empty`, `error`;
- защищать интерфейс от устаревших ответов при гонке запросов.

### 1.2. Ориентировочный план занятия

| Этап | Время | Содержание |
|------|-------|-----------|
| Постановка задачи | 5 мин | Почему данные больше не локальны и чем это меняет код. |
| Модель выполнения | 15 мин | Синхронный стек, микрозадачи, таймеры. Эксперимент с `event-loop.js`. |
| Promise и async/await | 15 мин | Состояния Promise, цепочки, try/catch, возврат из async-функции. |
| HTTP и fetch | 15 мин | Запрос, Response, статусы, заголовки, JSON. Особенность fetch: 404 ≠ reject. |
| URL и query | 10 мин | URL, URLSearchParams, кодирование, сохранение `false` и `0`. |
| Ошибки и отмена | 10 мин | Классификация (http / network / invalid-response / timeout / aborted), AbortController, тайм-аут. |
| Параллельность | 5 мин | Promise.all для независимых запросов. |

Распределение времени является ориентиром. При разборе ошибок и вопросов отдельные блоки могут занимать больше времени.

## 2. От синхронного кода к асинхронному

В ПР2–ПР4 любая операция возвращала результат сразу:

```javascript
const tasks = addTask(currentTasks, 20, "Новая задача", "high");
// tasks уже содержит обновлённый массив
```

Сетевая операция устроена иначе. Между отправкой запроса и получением ответа проходит время — от миллисекунд до секунд. Если бы JavaScript ждал ответа, весь интерфейс замер бы: не работали бы кнопки, не обновлялась бы анимация, не обрабатывались бы события.

Асинхронный код решает эту задачу: операция регистрируется, а продолжение выполняется позже, когда результат готов.

```javascript
const response = await fetch("http://127.0.0.1:5505/api/tasks");
// Здесь выполнение приостановилось, но процесс не заблокирован
const payload = await response.json();
console.log(payload.data);
```

Важно понимать: `await` не делает код синхронным. Он приостанавливает только текущую `async`-функцию, а остальной код и обработка событий продолжают работать.

### 2.1. Когда асинхронность обязательна

| Операция | Синхронная или асинхронная | Почему |
|----------|---------------------------|--------|
| Вычисление `2 + 2` | Синхронная | Результат известен сразу. |
| Обход массива из 1000 элементов | Синхронная | Всё в памяти процесса. |
| Чтение `localStorage` | Синхронная | Локальное хранилище браузера. |
| HTTP-запрос к серверу | Асинхронная | Ответ приходит по сети через неопределённое время. |
| Таймер `setTimeout` | Асинхронная | Выполнение откладывается. |
| Чтение файла большого размера | Асинхронная | В Node.js — через файловую систему. |

В ПР5 и далее все сетевые операции выполняются асинхронно. Это означает, что функция, которая обращается к API, не может вернуть данные напрямую — она возвращает `Promise`.

## 3. Модель выполнения

### 3.1. Три очереди выполнения

Для понимания порядка вывода полезно различать три вида задач:

1. **Синхронный стек** — код выполняется построчно до первого `await` или до завершения.
2. **Микрозадачи** — продолжения `Promise` (обработчики `.then`, `.catch`, `.finally`) и код после `await`. Выполняются сразу после опустошения синхронного стека, все до конца.
3. **Задачи** — обработчики таймеров (`setTimeout`, `setInterval`), событий DOM и другие. Выполняются после микрозадач.

```javascript
console.log("A: синхронный код");

setTimeout(() => {
  console.log("B: задача таймера");
}, 0);

Promise.resolve().then(() => {
  console.log("C: микрозадача Promise");
});

async function demonstrateAwait() {
  console.log("D: начало async-функции");
  await null;
  console.log("E: продолжение после await");
}
demonstrateAwait();

console.log("F: конец синхронного кода");
```

Ожидаемый порядок: `A`, `D`, `F`, `C`, `E`, `B`.

Разбор:

- `A`, `D`, `F` — синхронный код, выполняется сразу.
- Вызов `demonstrateAwait()` печатает `D`, затем встречает `await null` и приостанавливается. Продолжение `E` становится микрозадачей.
- `Promise.resolve().then(...)` регистрирует микрозадачу `C`.
- Синхронный стек пуст. Выполняются микрозадачи: `C`, затем `E`.
- Наконец, среда переходит к задачам — срабатывает таймер `B`.

### 3.2. Нулевая задержка таймера

`setTimeout(fn, 0)` не означает «выполнить немедленно». Это означает «поставить задачу в очередь с минимальной задержкой». Фактическая задержка зависит от среды и обычно составляет несколько миллисекунд. Задача всё равно выполнится после всех синхронных операций и всех микрозадач.

Это различие важно при отладке: если `console.log` после `fetch` выполняется раньше, чем ответ сервера, — это не ошибка, это штатное поведение асинхронного кода.

### 3.3. Ограничения упрощённой модели

Приведённая модель достаточна для понимания ПР5–ПР6. В реальных средах выполнения есть дополнительные фазы (например, `requestAnimationFrame`, `setImmediate` в Node.js, фазы `libuv`). Для учебного проекта различать синхронный код, микрозадачи и задачи — достаточно.

## 4. Promise и его состояния

### 4.1. Три состояния

`Promise` — объект, представляющий результат асинхронной операции. Он находится в одном из трёх состояний:

- **pending** — операция ещё не завершена.
- **fulfilled** — операция завершилась успешно, получено значение.
- **rejected** — операция завершилась с ошибкой, получена причина отказа.

После перехода в `fulfilled` или `rejected` состояние больше не меняется. Promise «устаканивается» (settled).

```javascript
const promise = fetch("http://127.0.0.1:5505/api/health");
console.log(promise instanceof Promise); // true
// Здесь promise ещё pending — ответ не получен
```

### 4.2. Цепочки обработчиков

Методы `.then`, `.catch`, `.finally` возвращают **новый Promise**. Это позволяет строить цепочки:

```javascript
fetch("http://127.0.0.1:5505/api/tasks")
  .then((response) => {
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    return response.json();
  })
  .then((payload) => {
    console.log("Задач:", payload.data.length);
  })
  .catch((error) => {
    console.error("Ошибка:", error.message);
  });
```

Ошибка в любом обработchain превращает возвращаемый Promise в rejected. Поэтому один `.catch` в конце может обработать отказы из всех предыдущих шагов.

### 4.3. `async` и `await`

`async`-функция всегда возвращает Promise. `await` приостанавливает выполнение только этой функции до урегулирования ожидаемого значения.

```javascript
async function loadTasks() {
  const response = await fetch("http://127.0.0.1:5505/api/tasks");
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }
  return response.json();
}

const tasksPromise = loadTasks();
console.log(tasksPromise instanceof Promise); // true
```

Ошибки обрабатываются через `try`/`catch`:

```javascript
try {
  const tasks = await loadTasks();
  console.log("Получено задач:", tasks.data.length);
} catch (error) {
  console.error("Не удалось загрузить:", error.message);
}
```

Пустой `catch` без анализа ошибки скрывает причину сбоя и в рабочем коде не используется.

### 4.4. Типичные ошибки при работе с Promise

**Ошибка 1. Данные используются без `await`:**

```javascript
const tasks = api.getTasks();
console.log(tasks.length); // TypeError: tasks — это Promise
```

**Ошибка 2. `await` вне `async`-функции:**

На верхнем уровне модуля это допустимо (top-level await), но внутри обычной функции — нет.

**Ошибка 3. Создание `new Promise` вокруг уже существующего Promise:**

```javascript
// Избыточно
const wrapped = new Promise((resolve) => {
  resolve(await fetch(url)); // SyntaxError
});
```

Если у вас уже есть Promise, его не нужно оборачивать.

## 5. HTTP-запрос и ответ

### 5.1. Основные понятия

HTTP-взаимодействие состоит из запроса и ответа. Для клиентского кода важны:

- **URL ресурса** — адрес, по которому делается запрос.
- **HTTP-метод** — `GET`, `POST`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`.
- **Заголовки** — метаданные (тип содержимого, авторизация, CORS).
- **Статус ответа** — числовой код результата.
- **Тело ответа** — данные (обычно JSON).

### 5.2. Группы статусов

| Группа | Смысл для клиента | Примеры |
|--------|------------------|---------|
| 2xx | Запрос обработан успешно | 200, 201, 204 |
| 3xx | Перенаправление | 301, 302 |
| 4xx | Ошибка клиента — неверный запрос | 400, 401, 404, 405 |
| 5xx | Ошибка сервера | 500, 502, 503 |

В ПР5 используются только `GET`. В ПР6 добавляются `POST`, `PATCH`, `DELETE`.

### 5.3. Контракт учебного API

Успешная коллекция:

```json
{
  "data": [
    {
      "id": 4,
      "title": "Подготовить модель задач",
      "completed": false,
      "priority": "high",
      "categoryId": 2
    }
  ],
  "meta": {
    "total": 1,
    "filters": {
      "completed": false,
      "priority": "high",
      "categoryId": 2,
      "q": ""
    }
  }
}
```

Ошибка:

```json
{
  "error": {
    "code": "TASK_NOT_FOUND",
    "message": "Задача с id 999 не найдена.",
    "details": { "id": 999 }
  }
}
```

Клиент использует стабильный машинный `code`, а не текст сообщения. Текст сообщения может меняться, код — часть контракта.

### 5.4. Рабочие маршруты

| Метод и путь | Результат |
|--------------|-----------|
| `GET /api/health` | Состояние учебного API. |
| `GET /api/tasks` | Все задачи или отфильтрованная коллекция. |
| `GET /api/tasks/:id` | Одна задача либо ошибка. |
| `GET /api/categories` | Все категории. |
| `GET /api/categories/:id` | Одна категория либо ошибка. |

Фильтры `/api/tasks`:

| Параметр | Допустимые значения | Пример |
|----------|---------------------|--------|
| `completed` | `true`, `false` | `?completed=false` |
| `priority` | `low`, `medium`, `high` | `?priority=high` |
| `categoryId` | положительное целое | `?categoryId=2` |
| `q` | строка до 100 символов | `?q=провер` |

Несколько фильтров применяются одновременно. Повторение параметра, неизвестный параметр и неверный тип дают `400 INVALID_QUERY`.

## 6. `fetch` и его особенности

### 6.1. Promise, а не значение

`fetch()` возвращает Promise с объектом `Response`. Это означает, что код после `fetch` выполнится до получения ответа:

```javascript
console.log("до");
const promise = fetch("http://127.0.0.1:5505/api/health");
console.log("после");
// Сначала выведется "до" и "после", ответ придёт позже
```

### 6.2. `fetch` не отклоняется при HTTP-ошибке

Это ключевая особенность. Ответ со статусом `404` или `503` обычно **не отклоняет** Promise: сервер доступен и отправил HTTP-ответ. Отклонение происходит только при сетевом сбое, неверной схеме URL или отмене запроса.

```javascript
const response = await fetch("http://127.0.0.1:5505/api/tasks/999");
console.log(response.status); // 404
console.log(response.ok);     // false
// Promise НЕ отклонился — нужно проверять явно
```

Поэтому проверка статуса обязательна:

```javascript
const response = await fetch(url);
if (!response.ok) {
  throw new Error(`HTTP ${response.status}`);
}
```

`response.ok` имеет значение `true` для статусов от `200` до `299`.

### 6.3. Заголовки и разбор JSON

До разбора успешного ответа проверяется `Content-Type`:

```javascript
const contentType = response.headers.get("content-type") ?? "";
if (!contentType.includes("application/json")) {
  throw new Error("Ожидался JSON");
}
const payload = await response.json();
```

`response.json()` также возвращает Promise и может завершиться ошибкой синтаксиса. Тело ответа читается один раз — повторный вызов `response.json()` или `response.text()` после первого чтения приведёт к ошибке.

Для статуса `204 No Content` тела нет. Попытка разобрать его как JSON завершится ошибкой. Клиент этой работы возвращает `null`, не пытаясь читать тело.

### 6.4. Корректный JSON ≠ корректные данные

Успешный `JSON.parse` означает только корректный синтаксис. Значение `{"data": "не массив"}` синтаксически корректно, но не соответствует контракту списка задач. Поэтому после разбора JSON выполняется проверка схемы:

```javascript
function isTask(value) {
  return (
    value &&
    typeof value === "object" &&
    Number.isSafeInteger(value.id) &&
    typeof value.title === "string" &&
    typeof value.completed === "boolean" &&
    ["low", "medium", "high"].includes(value.priority) &&
    Number.isSafeInteger(value.categoryId)
  );
}
```

## 7. URL и query-параметры

### 7.1. Не склеивать вручную

Фильтры GET-запроса передаются в URL:

```
/api/tasks?completed=false&priority=high
```

Строки не склеиваются вручную. Для кодирования используется `URLSearchParams`, доступный через объект `URL`:

```javascript
const url = new URL("http://127.0.0.1:5505/api/tasks");
url.searchParams.set("q", "API & ошибки");
console.log(url.href);
// http://127.0.0.1:5505/api/tasks?q=API+%26+%D0%BE%D1%88%D0%B8%D0%B1%D0%BA%D0%B8
```

### 7.2. Сохранение `false` и `0`

Значения `false` и `0` нельзя удалять проверкой `if (value)`: они могут быть содержательными. В контракте `buildUrl` пропускаются только `undefined`, `null` и пустая строка:

```javascript
function buildUrl(baseUrl, path, query = {}) {
  const url = new URL(path, baseUrl);
  for (const [key, value] of Object.entries(query)) {
    if (value !== undefined && value !== null && value !== "") {
      url.searchParams.set(key, String(value));
    }
  }
  return url.href;
}
```

### 7.3. Входной объект не изменяется

Функция формирования URL не должна мутировать переданный объект `query`. Это позволяет безопасно передавать замороженные объекты и объекты состояния.

## 8. Классификация ошибок

### 8.1. Почему недостаточно одного `catch`

При работе с сетью возможны разные виды отказов, и обработка у них разная:

| `kind` | Причина | Значимые поля |
|--------|---------|---------------|
| `http` | Сервер вернул статус вне 2xx | `status`, `code`, `details`, `url` |
| `network` | Ответ от сервера не получен | `cause`, `url` |
| `invalid-response` | Неверный `Content-Type`, JSON или схема | `cause`, `url` |
| `timeout` | Превышено время ожидания | `cause`, `url` |
| `aborted` | Запрос отменён внешним сигналом | `cause`, `url` |

HTTP-ошибка не должна повторно превращаться в сетевую из-за слишком широкого `catch`. Удобно отдельно перехватывать вызов `fetch`, а обработку полученного `Response` выполнять после него:

```javascript
let response;
try {
  response = await fetch(url, { signal });
} catch (error) {
  if (signal.aborted) {
    throw new ApiError("Запрос отменён", { kind: "aborted", cause: error });
  }
  throw new ApiError("Сеть недоступна", { kind: "network", cause: error });
}

if (!response.ok) {
  const payload = await response.json().catch(() => null);
  throw new ApiError(payload?.error?.message ?? `HTTP ${response.status}`, {
    kind: "http",
    status: response.status,
    code: payload?.error?.code ?? null,
    details: payload?.error?.details ?? null,
  });
}
```

### 8.2. Класс `ApiError`

Вместо анализа случайных текстов используется собственный класс ошибки с полем `kind`:

```javascript
class ApiError extends Error {
  constructor(message, { kind, status = null, code = null, details = null, url = null, cause }) {
    super(message, cause === undefined ? undefined : { cause });
    this.name = "ApiError";
    this.kind = kind;
    this.status = status;
    this.code = code;
    this.details = details;
    this.url = url;
  }
}
```

Такой подход позволяет в интерфейсе показывать разные сообщения для разных видов ошибок и не смешивать их с внутренними исключениями.

## 9. Ограничение времени и отмена

### 9.1. `fetch` не задаёт тайм-аут автоматически

Если сервер не отвечает, запрос может висеть неопределённо долго. Для ограничения времени используется `AbortSignal.timeout()`:

```javascript
const response = await fetch(url, {
  signal: AbortSignal.timeout(3000),
});
```

### 9.2. Явная отмена через `AbortController`

Для отмены запроса по действию пользователя (например, смена фильтра) используется `AbortController`:

```javascript
const controller = new AbortController();
const pending = fetch(url, { signal: controller.signal });
controller.abort();
await pending; // отклонится с ошибкой AbortError
```

### 9.3. Объединение сигналов

Если одновременно поддерживаются внешний сигнал и тайм-аут, сигналы можно объединить через `AbortSignal.any()`:

```javascript
const combined = AbortSignal.any([externalSignal, AbortSignal.timeout(3000)]);
```

Клиент различает `timeout` и `aborted`: первый — истекло заданное время, второй — вызывающий код отменил операцию.

### 9.4. Отмена при смене фильтра — штатное управление

Когда пользователь быстро меняет фильтры, предыдущий запрос теряет смысл. Его отмена — это не ошибка, а управление потоком. Поэтому сообщение об ошибке пользователю при `kind === "aborted"` не выводится.

## 10. Параллельная загрузка

### 10.1. Последовательное и совместное ожидание

Если второй запрос зависит от результата первого, используется последовательность:

```javascript
const task = await api.getTaskById(25);
const related = await loadRelated(task.categoryId);
```

Если ресурсы независимы, оба запроса можно начать до ожидания:

```javascript
const tasksPromise = api.getTasks();
const categoriesPromise = api.getCategories();
const [taskResult, categories] = await Promise.all([
  tasksPromise,
  categoriesPromise,
]);
```

### 10.2. `Promise.all` не создаёт параллельность

`Promise.all` не запускает операции — он ожидает уже переданные значения Promise. Если передать сами функции без вызова, запросы не начнутся:

```javascript
// Неправильно: функции не вызваны
await Promise.all([api.getTasks, api.getCategories]);

// Правильно: запросы уже запущены
await Promise.all([api.getTasks(), api.getCategories()]);
```

### 10.3. Отказ одного из Promise

При отказе одного из Promise внутри `Promise.all` итоговый Promise отклоняется. Остальные операции автоматически не отменяются — они продолжат выполняться, но их результаты будут отброшены.

## 11. Разделение общего и предметного клиента

### 11.1. Транспортный уровень

`api-client.js` не знает, что такое задача. Он отвечает за транспорт:

```
путь + параметры
      ↓
     fetch
      ↓
статус и Content-Type
      ↓
   JSON / ApiError
```

Его задача — сформировать URL, выполнить `GET`, проверить `Response`, разобрать JSON и преобразовать ошибки в `ApiError`.

### 11.2. Предметный уровень

`task-api.js` знает маршруты и схему:

```
getTasks(filters) ───────→ /tasks
getTaskById(id) ─────────→ /tasks/:id
getCategories() ─────────→ /categories
loadInitialData(filters) → Promise.all
```

Этот модуль позже можно вызвать из DOM-интерфейса или React-компонента без копирования кода `fetch`.

### 11.3. Подмена `fetch` в модульной проверке

В `createApiClient` функция `fetchFn` передаётся аргументом:

```javascript
const client = createApiClient({
  baseUrl,
  fetchFn: fakeFetch,
});
```

Проверка может вернуть подготовленный `Response`, зафиксировать URL и смоделировать ошибку без запуска сети. Интеграционный набор отдельно подтверждает совместимость с настоящим локальным API.

## 12. Состояния асинхронного интерфейса

### 12.1. Четыре состояния

В ПР6 одного массива задач недостаточно. Интерфейсу также требуется знать, идёт ли загрузка и почему список пуст.

| Состояние | Значение | Представление |
|-----------|----------|---------------|
| `loading` | Ответ ещё не получен | Сообщение о загрузке, `aria-busy="true"` |
| `ready` | Получен непустой список | Карточки и число найденных задач |
| `empty` | Запрос успешен, результатов нет | Явное сообщение без старых карточек |
| `error` | Запрос завершился ошибкой | Понятное сообщение и кнопка повтора |

`empty` не считается ошибкой. Это нормальный результат фильтра или действительно пустого набора.

### 12.2. Блокировка при мутации

Изменяющая операция имеет дополнительное состояние ожидания. На это время соответствующие кнопки блокируются, чтобы двойной щелчок не создал два одинаковых запроса.

### 12.3. Сервер как источник истины

После `POST`, `PATCH` или `DELETE` приложение повторно выполняет `GET /tasks` с текущими фильтрами. Такой пессимистический сценарий показывает только подтверждённое сервером состояние:

```
действие → блокировка → запрос изменения → успешный ответ
        → повторный GET с текущими фильтрами → отрисовка → разблокировка
```

В ПР6 локальная копия не записывается в `localStorage`. Данные принадлежат API, а массив в контроллере является только снимком последнего ответа.

## 13. Гонка запросов

### 13.1. Проблема

Если два запроса запущены подряд, первый может завершиться позднее второго. Без защиты старый результат перезапишет новый фильтр.

### 13.2. Два механизма защиты

Используются два механизма:

1. Предыдущий запрос отменяется через `AbortController`.
2. Каждому запуску присваивается последовательный номер, и результат применяется только при совпадении с последним номером.

Вторая проверка нужна даже при отмене: тестовый клиент, кэш или другая реализация источника может завершить операцию, не отреагировав на сигнал немедленно.

```javascript
let loadNumber = 0;
let activeController = null;

async function loadTasks(filters) {
  if (activeController) activeController.abort();
  const controller = new AbortController();
  activeController = controller;
  const currentLoad = ++loadNumber;

  try {
    const result = await api.getTasks(filters, { signal: controller.signal });
    if (currentLoad !== loadNumber) return; // устаревший ответ
    renderReady(result);
  } catch (error) {
    if (currentLoad !== loadNumber) return;
    if (error.kind === "aborted") return; // штатная отмена
    renderError(error);
  }
}
```

### 13.3. Отмена при размонтировании

В ПР6 при размонтировании компонента или смене фильтра предыдущий запрос отменяется. Это ожидаемое управление потоком, поэтому сообщение об ошибке пользователю не выводится.

## 14. CORS и граница ПР5

### 14.1. Что такое CORS

CORS (Cross-Origin Resource Sharing) применяется браузером к запросам между разными origin. Origin определяется схемой, хостом и портом. Адреса `http://127.0.0.1:5505` и `http://127.0.0.1:5506` относятся к разным origin.

### 14.2. Ограничения лекции

Сервер заготовки отправляет разрешающие заголовки для будущей ПР6. Запросы Node.js из ПР5 не являются проверкой браузерной политики CORS.

Режим `no-cors` не используется как способ исправления CORS: в браузере он ограничивает запрос и делает ответ непрозрачным для JavaScript. Настройка разрешённых origin относится к серверу.

## 16. Связь с практическими работами

### 16.1. ПР5: Асинхронные операции и получение данных с сервера

В ПР5 основные идеи лекции применяются к модулю запросов:

- создаётся `api-client.js` с классификацией ошибок;
- создаётся `task-api.js` с проверкой схемы данных;
- реализуется `buildUrl` с сохранением `false` и `0`;
- реализуется параллельная загрузка через `Promise.all`;
- проверяется работа с тайм-аутом и явной отменой;
- пользовательский интерфейс пока не подключается — это граница ПР6.

### 16.2. ПР6: Подключение браузерного приложения к API

В ПР6 приложение получает следующий уровень поведения:

- DOM-интерфейс подключается к API;
- CRUD через HTTP (POST, PATCH, DELETE);
- состояния loading/ready/empty/error;
- гонка запросов и отмена предыдущего;
- повторный GET после мутации;
- валидация формы до отправки.

Главный переход между работами: ПР5 отвечает на вопрос «как получить данные и обработать ошибки», а ПР6 — «как связать это с пользовательским интерфейсом».

## 17. Итоги

- Асинхронная операция представляется Promise; `await` не делает код синхронным.
- Порядок выполнения: синхронный стек → микрозадачи → задачи.
- Нулевая задержка таймера — минимальная, не немедленная.
- `fetch` не отклоняется при HTTP-ошибке — проверка `response.ok` обязательна.
- 204 No Content нельзя разбирать как JSON.
- URL и query формируются стандартными средствами; `false` и `0` сохраняются.
- Ошибки классифицируются по `kind`; HTTP-ошибка не маскируется сетевой.
- `AbortController` отменяет запрос, но не гарантирует мгновенную остановку.
- `Promise.all` ожидает уже запущенные Promise, не отменяет остальные при отказе.
- Интерфейс должен различать loading, ready, empty и error.
- После мутации выполняется повторный GET; сервер — источник истины.
- Гонка запросов требует и отмены, и проверки актуальности результата.
- Общий HTTP-клиент отделён от предметного API для переиспользования.
- CORS проявляется в браузере, но не в Node.js.
